# v8.2.7 Windows first-run readiness

Status: candidate under qualification. This document records observed behavior,
the fixes in the candidate, and what still has to pass before a release tag.

## What happened on the fresh Windows PC

On 2026-11-27 a new v8.2.6 Windows profile imported the bundled full-v6
snapshot at height 167,856. The network tip and peers became available, but
`wallet.createhd` for `sabina` returned `orchard_history_pending`: the RPC
explicitly said that no wallet had been created. The snapshot authenticates
current chain state; it does not contain the earlier Orchard block history
needed by the current wallet creation path. The node fetched and verified that
history separately. The active data directory was created around 19:10 local
time, its Orchard history cache around 19:35, and the `sabina` wallet around
21:05. The seed screen appeared by 21:06. The elapsed time was roughly 115
minutes from profile start and 90 minutes from history-cache creation. These
are approximate wall-clock observations, not a profiler trace.

The cache contained about 18,956 files near completion. That count is **not**
a verified height or percentage. We did not capture the RPC's
`orchard_history.verified_height` and `target_height` during this run. The
precise bottleneck among peer transfer, catalog transfer, replay, cache I/O and
Windows-specific overhead is not yet established. The wallet eventually
completed without restarting Dinero, which rules out a permanent stall in this
one run. A new wallet on an already-synced Mac profile was created in seconds;
that comparison does not isolate an operating-system defect.

An earlier `dinero-cli` diagnostic failed to load the cookie from `.dinero`.
The Windows GUI daemon's default data directory is `%APPDATA%\Dinero`. That
was a CLI default-path mismatch, separate from the GUI wallet delay. It did
not show that the daemon was down or that its cookie was in the wrong place.

After creation, `sabina` was selected with a zero confirmed balance, as
expected for a new wallet. Orchard briefly showed `Reading...` and P2MR showed
0%; we did not confirm whether these settled. The chain height at the beginning
of bootstrap and the wallet-history readiness are distinct states. Solo CPU
mining was running with two threads after setup. We did not establish whether
it started automatically or was started by the user, so do not infer an
auto-mining bug from that observation. The user asked that it be left running.

## Candidate changes from this incident

- Show Orchard verified/target block progress on the create-wallet page and
  say that setup continues automatically. When all blocks have arrived but
  the final history state is unverified, show final verification instead of a
  misleading 100% completion.
- Retry only typed `snapshot_bootstrap_pending` and `orchard_history_pending`
  refusals that guarantee no wallet was created. Retry while the page stays
  open, even past one hour. Close, nonretryable errors and successful creation
  stop retries. Transport ambiguity never authorizes another create request.
- Keep the 12 recovery words hidden until the person clicks Reveal Seed. Use a
  clear, calmer privacy reminder; add Slovenian translations for the new
  first-run messages. The words still must be written down privately.
- Use `%APPDATA%\Dinero` as the native Windows CLI default and exercise both
  GUI-default and explicit data-directory cookies in Windows CI.
- In the append-only Orchard history verifier, reuse the prior block's
  validated commitment digest/count tuple as the next block's input. It still
  performs the full, MAC-checked post-append spool scan for every block and
  preserves the existing event/rewind path. This removes one growing spool
  scan per block. The verifier also reuses its bounded SQLite statements so
  each scan page does not reprepare the same query. Their effect on Windows
  first-run time has not been measured yet.

The UI changes improve clarity and diagnostics. The spool-scan change has a
plausible performance benefit, but does **not** yet establish that the
90-minute Orchard wait has been shortened. Issue #990 tracks that work;
issue #991 tracks the CLI default path.

## Other incidents and boundaries

- An older H52,287 snapshot wallet can show zero despite historical payouts
  because its wallet index was started from an older source. Its funded-wallet
  recovery remains a separate, safety-sensitive problem. A fresh v6 snapshot
  is appropriate for a proven-empty new profile, but moving funded wallet
  files to it without a complete rescan can hide coins. See
  `docs/plans/2026-11-26-legacy-snapshot-wallet-recovery.md`.
- The pool miner's displayed session work and reported block cadence, and the
  AFA1835 balance screenshot, were **not** reproduced or diagnosed on this
  Windows PC. They require their own pool-versus-chain evidence. Session work
  is not a confirmed on-chain wallet balance.
- The repeated RustDesk windows came from the remote-support attempt. They
  are not evidence of a Dinero daemon or wallet fault. The friend requested
  disconnection; no further access is authorized by this incident.

## Release gates

1. Measure a clean, installed Windows first run with the exact candidate:
   snapshot import, network-tip progress, Orchard requested/verified/target
   heights over time, catalog/body transfer and verification time, and time to
   one successful named wallet with all promised receiver types. Determine an
   acceptable latency target and demonstrate a real speed improvement; a
   progress bar alone cannot close #990.
2. Confirm the wizard does not create a duplicate wallet after a timeout or
   cancellation, does not expose recovery words before Reveal Seed, and stops
   retrying on a nonretryable result. Confirm the Slovenian and English paths
   on Windows, including the final-verification message.
3. Confirm a new wallet is spendable and persists after restart, and that
   Orchard and P2MR loading states settle. Verify mining payout destination
   and maturity before treating a rising miner estimate as wallet funds.
4. Preserve the old-profile admission and funded-recovery boundary. Test both
   a truly empty old profile and a profile with wallet files or past payouts;
   no automatic deletion or silent switch may occur.
5. Pass all relevant Windows, macOS and Linux tests on the exact reviewed
   commit, including installed signed Windows package checks, snapshot
   provenance, wallet recovery and daemon startup. Archive the results and
   checksums before tagging and attaching a release.

The 2026-11-27 Windows candidate CI run was started from commit `465276343`,
before the later CLI, seed-privacy and wording changes. Its result cannot
qualify a newer commit; a new exact-source run is required.
