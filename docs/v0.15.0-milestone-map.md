## Overview

v0.15.0 implements **Utreexo input-spend enforcement**, completing the transition to full stateless validation. Blocks now carry proofs that validate input spending without requiring nodes to store the full UTXO set.

**Why Now (Prerequisites Met)**:
- ✅ Utreexo AFTER-state commitments enforced (v0.14.0.4)
- ✅ Mining and block assembly operational (v0.14.0)
- ✅ Mempool validates transactions (v0.11.0)
- ✅ Network relay works (v0.13.0)
- ✅ Output commitments proven correct (v0.14.0.4)

**Scope**: Input spending validation via Utreexo proofs (full stateless validation)

## Architecture Constraints

### What v0.15.0 Does

**Proof Data in Blocks**:
- Blocks include Utreexo proofs for all inputs
- Proof format: Merkle inclusion proofs for spent outputs
- Serialization: Extend block format with proof data field
- Bridge nodes: Serve proofs to light clients

**Mempool Proof Validation**:
- Transactions submitted with proofs
- Mempool validates proofs before acceptance
- Invalid proofs → transaction rejected
- No proof → relay to bridge node for proof retrieval

**ConnectBlock Validation**:
- Validate input spending via Utreexo proofs
- Verify proofs against current accumulator state
- Update accumulator (add outputs, delete inputs)
- Reject blocks with invalid proofs

**Bridge Node Functionality**:
- Maintain full UTXO set (for proof generation)
- Serve proofs to light clients on request
- Convert legacy blocks to Utreexo blocks
- RPC: `getutreexoproof <txid> <vout>`

### What v0.15.0 Does NOT Do

🚫 **Out of Scope**:
- Light client wallet (just proof serving infrastructure)
- P2P protocol changes (BIP155 Utreexo service bit)
- Compact proofs (optimization for later)
- Historical proof archival (prune old proofs)
- Multi-block proof batching
- Zero-knowledge proof integration

These are polish/optimization work, not architecture.

### v0.15.0.2 — Mempool Proof Validation (OPTIMIZATION)

**Goal**: Mempool validates Utreexo proofs before accepting transactions

**Rules**:
- Transactions submitted with proofs via RPC
  - `sendrawtransaction <hex> [utreexoproof_hex]`
  - If no proof provided, try to generate proof locally (bridge mode)
  - If no proof and not bridge, reject transaction
- Validate proofs against current accumulator
  - Extract leaf data from proof
  - Verify Merkle path against accumulator root
  - Ensure all inputs have valid proofs
- Store proofs in mempool
  - Needed for block template construction
  - Discard after confirmation

**Deliverables**:
- Extend `Mempool::addTransaction()` to validate proofs
- RPC: `sendrawtransaction` accepts proof parameter
- Proof cache in mempool entries
- Unit tests for proof validation

**Exit Criteria**:
- ✅ Mempool validates proofs before acceptance
- ✅ Transactions without proofs rejected (non-bridge mode)
- ✅ Invalid proofs rejected with clear error
- ✅ Bridge mode can generate proofs on-the-fly

**Files Expected**:
- `include/daemon/mempool.h` (modified)
- `src/daemon/mempool.cpp` (modified - proof validation)
- `src/rpc/methods_mempool_context.cpp` (modified - sendrawtransaction)

**Pattern**: Optimization layer - build on foundation, prove correctness

### v0.15.0.3 — ConnectBlock Input Validation (CONSENSUS)

**Goal**: Blocks with invalid proofs rejected at consensus layer

**Rules**:
- ConnectBlock validates all input proofs
  - Extract proofs from block
  - For each transaction input:
    - Verify proof against current accumulator
    - Validate leaf data (amount, scriptPubKey)
    - Check signature using validated data
  - Update accumulator (add outputs, delete inputs)
- Reject blocks with:
  - Missing proofs
  - Invalid proof (bad Merkle path)
  - Proof for non-existent UTXO
  - Mismatched leaf data

**Deliverables**:
- Extend `BlockValidator::ConnectBlock()` for proof validation
- Proof extraction from blocks
- Integration with Utreexo accumulator
- Consensus test suite

**Exit Criteria**:
- ✅ Blocks with invalid proofs rejected
- ✅ Blocks with valid proofs accepted
- ✅ Accumulator updated correctly
- ✅ Reorg handling works (accumulator rollback)

**Files Expected**:
- `src/consensus/block_validation.cpp` (modified - proof validation)
- `include/consensus/block_validation.h` (modified)

## Design Principles

**Statelessness**:
- Light nodes store only accumulator (32 bytes)
- Bridge nodes provide proofs
- No UTXO set required for validation (only for proof generation)

**Proof Efficiency**:
- Minimize proof size (compress Merkle paths)
- Batch proofs for multiple inputs (single accumulator state)
- Version byte for future optimizations

**Backward Compatibility**:
- Legacy blocks (without proofs) still validate via UTXO set
- Bridge nodes can serve both modes
- Gradual migration path

**Security**:
- Invalid proofs → block/transaction rejected
- Proof must match current accumulator state
- Leaf data must match UTXO data

---

## Utreexo Patterns Preserved

**Proof Structure**:
- Merkle path: Array of hashes from leaf to root
- Leaf data: (txid, vout, amount, scriptPubKey)
- Siblings: Hashes needed to compute root

**Accumulator Updates**:
- Add outputs: Append to leaves, update root
- Delete inputs: Mark as spent, update root
- Deterministic: Same blocks → same accumulator state

**Bridge Node Role**:
- Maintains full UTXO set (for proof generation)
- Serves proofs to light clients
- Converts legacy blocks to Utreexo blocks

## Critical Design Decisions

### 1. Proof Data Location
**Decision**: Store proofs in blocks (not separate)
**Rationale**:
- Proofs are consensus-critical
- Block must be self-contained for validation
- Simplifies reorg handling

### 2. Bridge vs. Light Node Distinction
**Decision**: Bridge nodes maintain full UTXO set
**Rationale**:
- Proof generation requires UTXO set
- Light nodes can be truly stateless
- Clear separation of responsibilities

### 3. Proof Validation Point
**Decision**: Validate proofs in ConnectBlock (not CheckBlock)
**Rationale**:
- Requires accumulator state (available in ConnectBlock)
- CheckBlock is stateless header validation
- Matches Bitcoin Core validation flow

### 4. Mempool Proof Storage
**Decision**: Store proofs in mempool entries
**Rationale**:
- Needed for block template construction
- Proofs discarded after confirmation
- Mempool is ephemeral (okay to store temporarily)

### 5. Backward Compatibility
**Decision**: Legacy blocks (without proofs) still validate
**Rationale**:
- Gradual migration path
- Don't break existing nodes
- Bridge nodes can serve both modes

## Implementation Notes

### Proof Size Estimates
- **Per input**: ~1KB (Merkle path ~32 levels)
- **Per transaction**: 1-3KB (average 2 inputs)
- **Per block**: 2-10KB (average ~5 transactions)

**Target**: Keep proofs under 10KB per block (acceptable overhead)

### Accumulator State
- **Size**: 32 bytes (SHA256 root)
- **Storage**: In-memory (no disk required for light nodes)
- **Update frequency**: Every block

### Bridge Node Requirements
- **UTXO set**: Full set required (same as current full nodes)
- **CPU**: Proof generation is O(log N) per input
- **Network**: Serve proofs on request (minimal bandwidth)

## Security Considerations

### Proof Validation
- ✅ Invalid proofs → reject block/transaction
- ✅ Proof must match current accumulator
- ✅ Leaf data must match UTXO data
- ✅ No double-spend via fake proofs

### Accumulator Security
- ✅ Deterministic updates (same blocks → same accumulator)
- ✅ Cryptographically binding (SHA256 Merkle tree)
- ✅ Cannot forge proofs without UTXO set

### DoS Protection
- ✅ Reject invalid proofs early (before full validation)
- ✅ Rate limit proof requests to bridge nodes
- ✅ Max proof size limit (prevent bloat)
