# Shielded protocol v1 — independent interoperability vectors

Status: consensus guardrail for the deployed v1 encoding. These vectors do
not activate a new rule and do not change any accepted transaction.

## Why this exists

Most pre-existing shielded tests generate an object with the Dinero C++ code
and verify it with the same implementation. That is valuable regression
coverage, but a writer and reader can share the same mistake. The checked-in
fixture at `tests/vectors/shielded_protocol_v1_external.json` is generated by
`scripts/generate_shielded_protocol_vectors.py`, a standard-library-only
Python implementation. It imports no Dinero module and links no Dinero crypto
library. The C++ test treats the JSON values as external literals and compares
production results byte for byte.

The generator is deterministic. Regenerate and verify with:

```sh
python3 scripts/generate_shielded_protocol_vectors.py --self-test
python3 scripts/generate_shielded_protocol_vectors.py --check --self-test
ctest --test-dir build -R '^ShieldedProtocol(ExternalVectors|Oracle)$' --output-on-failure
```

`--check` is the normal CI mode. It refuses any difference between a fresh
independent derivation and the committed JSON.

## Covered interfaces

The fixture pins:

- all Poseidon round constants, all 65 states for `(0,0)` and `(1,2)`, and
  both final outputs;
- BIP32 account derivation, spending/viewing keys, even-Y normalisation,
  diversifier generation, hash-to-point, diversified public keys and Bech32m
  mainnet/testnet/regtest addresses;
- note plaintext layout, recipient ECDH, HKDF inputs, nonce, associated data,
  ChaCha20-Poly1305 ciphertext and tag, and the complete 611-byte encrypted
  note;
- note commitments and nullifiers at leaf indexes zero and `UINT64_MAX`;
- Fiat–Shamir framing and challenge output for proof versions `0x01` through
  `0x05`, including the dormant spend-authorisation transcript form;
- parseable Spartan, Hyrax commitment, Hyrax evaluation and IPA container
  encodings made from valid secp256k1 point encodings;
- shielded transaction sighash, binding sighash, Pedersen binding-key
  commitment and deterministic BIP340 binding signature;
- aggregate range-proof containers, including the 252/253-byte CompactSize
  boundary;
- canonical shield, transfer and unshield bundle bytes and their complete v6
  transaction envelopes in witness and non-witness serialization modes;
- parser acceptance of canonical bundles and distinguished rejection of
  truncation, trailing data, non-minimal CompactSize and descending spends;
- commitment-tree empty, append, truncate, reset and reapply roots.

Proof bytes embedded in the shield/transfer/unshield bundles are deliberately
short serialization sentinels. Those transaction fixtures pin the wire format;
they are not represented as valid zero-knowledge proofs or consensus-valid
economic transactions.

## What this does not claim

This is not a second Spartan/Hyrax prover and not a second Borromean range-
proof prover. It independently pins their transcript and container boundaries;
proof validity remains covered by the production prover/verifier suites.

Outgoing-view recovery is not covered because the current protocol does not
implement it. Recipient decryption is covered. Adding an outgoing plaintext,
`ovk`-derived recovery key, sender recovery algorithm and corresponding
negative vectors is a future protocol change, not something a vector file can
invent safely.

Gate E snapshot-section and coinbase-Merkle binding are intentionally excluded.
That work changes the snapshot trust boundary and must own its own versioned
vectors. Keeping it out of this fixture lets this interoperability gate land
without touching or racing the Gate E implementation branch.

The historical 96-byte all-zero wallet placeholder is also excluded. The only
canonical addressed-note encoding pinned here is the production 611-byte form
(`epk[32] || ciphertext[563] || tag[16]`). A legacy placeholder must never gain
protocol legitimacy merely because a compatibility path still recognizes it.

## Review rule

Changing a checked-in byte requires all of the following in the same review:

1. the normative rule that changed;
2. the independent Python derivation change;
3. the C++ production or conformance-test change;
4. an explicit compatibility and activation assessment.

A test-only update of the JSON is not an acceptable way to make CI green.
