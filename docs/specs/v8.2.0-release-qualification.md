## What the package checks establish

`--orchard-build-info` and `scripts/verify-orchard-package.py` check the linked
protocol profile/backend and whether Orchard screens were compiled in. They exit
before GUI/node startup. They do not attest the entire source tree, dependency
version, runtime readiness or payment behavior. Bind these results to the exact
build records and final artifact hashes; do not treat the JSON alone as proof
that an artifact includes every qualified fix.

The new Qt deployment helper operates on a private filtered plugin copy. Its
native check re-deployed a relocated copy of an existing qualified bundle,
verified the ad-hoc signature and read compiled capabilities while preserving
the installed toolkit's plugins. It did not create or notarize a final installer,
rebuild the full application, start its node or qualify a new platform.

## Execution and rollout controls

Public source publication and general CI dispatch remain held pending the
reviewed execution scope. A narrowly authorized component workflow does not
permit a root desktop workflow, broad test suite or release publication. Keep
completed builds and evidence immutable and use fresh outputs for changed
sources. Retain failures, actual executed-test counts and instrumentation limits.
Do not weaken tests, deadlines, validation or synchronization to obtain a pass.

Production nodes, fleet operations, phones, Swift changes, deployment, merges
and activation are outside the current execution authorization. Preparation and
local engineering continue independently. New runtime work must use its explicitly
approved isolated scope; completed four-case HTTP permission is not general
permission for other listeners or probes. The vault fee-payer decision remains
open; do not infer a choice from general permission to continue development.

Before release, recheck that 150,000 leaves a sufficient upgrade window using
then-current readiness and upgrade coverage; revise the reviewed source schedule
if it does not. Verify the network's actual
hash-rate headroom against the ASERT target floor before choosing that boundary. Review the public release
profile, mixed-version behavior and rollback/incident plan. Publish reviewed
release notes and checksums with the final manifest. Readiness verification and
rollout remain separate actions requiring their applicable authorization.

## Independent mobile ASERT and compact-validation handoff

Use the **final qualified node source**, not the historical daemon pin above, as
the reference. Relevant code includes `include/consensus/asert.h`,
`include/consensus/pow_context.h`, `include/consensus/block_timing.h`,
`tests/consensus/sixty_second_asert_probe.cpp` and
`tests/consensus/test_sixty_second_asert_oracle.py`.

The independent validator must match height-aware elapsed time, the candidate
branch's A-1 anchor, fractional polynomial scaling, saturation before overflow,
target clamping and target encoding. Preserve historical preactivation rules;
changing spacing alone is insufficient. Network parameters must come from
reviewed local configuration or an independently authenticated versioned release
configuration. A remote RPC response may cross-check configuration, but must not
choose validation rules or authorize bypassing difficulty or Utreexo checks.

Required final evidence includes:

- Independent oracle agreement for historical/disabled rules and A-1/A/A+1,
  negative time differences, half-life edges, overflow, rounding and target floor.
- Header validation on competing branches with different anchors, restart and
  rollback across activation; missing ancestry must defer until verified.
- Exact compact/Orchard format and rejection behavior on every supported mobile
  path, retaining existing header/root/proof validation.
- Reviewed real-time effects of 60-second blocks on proof refresh, confirmation
  displays and other block-count policies. Do not change consensus maturity or
  substitute a wall-clock promise for a block-count policy without review.

Keep the selected 100-block coinbase maturity and the existing six-confirmation
UI policy unchanged unless a separate reviewed decision changes them.

Legacy shielded-holder recovery is outside the agreed release work. This does
not waive transparent-key preservation, new Orchard ownership, or consistent
retirement and supply accounting. Do not present the new pool as an automatic
migration of legacy balances.
