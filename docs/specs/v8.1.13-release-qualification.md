## Remaining sequence

1. Independent review of the canonical compact format and ASERT transition:
   signed version/transcript domains, malformed encoding, historical behavior,
   target encoding/rounding, the branch-specific A-1 anchor, timestamps and floor.
2. Compile/package the exact daemon, wallet/embedded and miner artifacts across
   supported platforms. Exercise those downloaded binaries; update sidecar hash
   locks only with measured final hashes. Full ARM/mobile and GPU runtime
   qualification is distinct from the vector and build checks already passed.
   DineroDPI's independent Swift header validator needs the compatibility gate
   below before timing activation.
3. Run a PoW-enforced isolated network with hash-rate changes, partitions,
   reconnect/failover, compact transactions and a CSN. Measure stale work,
   block propagation, worst-case validation and template-selection throughput.
4. Test snapshot/import and boundary-header backfill, mixed versions and recovery
   contingencies. Verify the actual network's hash headroom against ASERT's
   target floor before selecting an activation boundary.
5. After production format/activation wiring is reviewed and all gates pass,
   bind the final sources and artifacts into the v8.1.13 release manifest,
   deploy activation-aware binaries, verify readiness, then activate at the
   earliest coordinated future height. Owner authorization already exists.

The current compact implementation remains regtest-only and timing activation
remains disabled. These packaging candidates establish distribution plumbing;
they are not the final production-format binaries. Nonempty solo/JD remains a
separate protocol implementation and qualification item if advertised.

## DineroDPI Swift ASERT compatibility handoff

The mobile audit reports a live Swift ASERT implementation with 120-second
spacing. Its source was not available in this checkout, so the mobile owner
must verify the reported call paths in the DineroDPI repository. The proposed
parallel scope is one focused, test-first Swift implementation and review PR;
the daemon and packaging work remain in their existing lane.

Use the merged daemon commit above as the initial reference. Relevant sources
are `include/consensus/asert.h`, `include/consensus/pow_context.h`,
`include/consensus/block_timing.h`, `tests/consensus/sixty_second_asert_probe.cpp`
and `tests/consensus/test_sixty_second_asert_oracle.py`. Port the complete
activated behavior: height-aware expected elapsed time, the candidate branch's
own A-1 anchor, fractional polynomial scaling, saturation before overflow,
target clamping and byte-normalized target encoding. Preserve every historical
preactivation arithmetic and encoding rule. Changing spacing alone is not
sufficient. Requalify against the final reviewed daemon revision if it changes.

Consensus parameters must come from the app's reviewed network configuration
(or an independently authenticated and versioned release configuration).
`getconsensusinfo` can cross-check that configuration, but a remote endpoint
must not select activation heights or validation rules for the app. Display
configuration mismatches; never bypass difficulty or Utreexo validation to
recover. Keep production activation disabled until the coordinated release
chooses the reviewed boundary. Explicit test-network overrides are separate.

Required evidence:

- Red-to-green tests and exact Swift/daemon output agreement using independent
  ASERT oracle cases, including historical and disabled-upgrade vectors.
- A-1/A/A+1, negative time differences, fractional and whole half-life edges,
  target floor/overflow/rounding and the daemon's timestamp reference rules.
- Real header validation across activation and competing branches with
  different A-1 anchors; restart and rollback below/above activation.
- Missing boundary ancestry must defer/fetch without accepting an unvalidated
  header, then resume when verified history is available. Wrong RPC settings
  must not alter locally selected consensus rules.
- Existing Utreexo header/root/proof checks remain enforced throughout.

Keep the selected 100-block coinbase maturity unchanged. Leave the reported
six-confirmation UI policy unchanged pending a separate product decision.
Compact-transaction parsing is a separate required gate before production
compact activation; verify its actual serialized layout and rejection behavior
against the final format rather than changing version tags or note-container
sizes speculatively. Fee copy and unused constants can follow separately.
