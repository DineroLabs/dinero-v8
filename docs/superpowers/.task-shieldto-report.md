# Shield-to-recipient — implementation report

**Branch:** `feat/shield-to-recipient`
**Status:** DONE — roundtrip gate PASSES (validator accepts + recipient decrypts).

## What was extracted (shared helper)

`BuildAddressedRecipientOutput(recipient, memo, cv_bound, rcm_override?, esk_override?)`
in `src/wallet/shielded_wallet_ops.cpp` (declared in
`include/wallet/shielded_wallet_ops.h`). This is the addressed-recipient
output construction lifted **verbatim** out of
`BuildAddressedTransferBundleForTx`:

- `rcm` fresh CSPRNG (or override for deterministic test vectors)
- `pk_note = Poseidon(DeriveNoteSpendKey(rcm), 0)`
- `commitment = NoteCommitment(d_packed, pk_note, value, rcm)`
- `encrypted_note = EncryptNoteForRecipient(d, pk_d, {d,value,rcm,memo})`
- Spartan output proof (`cv_bound`-aware) + fresh Pedersen `rcv` + rangeproof `nonce`

`BuildAddressedTransferBundleForTx` now calls this helper for its recipient
output — a mechanical extraction preserving the exact `RandomHash()` call
order (rcm → rcv → nonce). Returns `AddressedRecipientOutput { status, error,
PlannedOutput planned, Hash commitment }`.

The `rcm_override`/`esk_override` params follow the existing
`EncryptNoteForRecipient(..., esk_override)` precedent — test-only
determinism; production passes nullptr.

## New op (transparent → external dins1)

- **Pure builder** `BuildAddressedShieldBundleForTx(tx, recipient, memo?, cv_bound)`
  in `shielded_wallet_ops.cpp`. Mirrors `BuildShieldBundleForTx` (transparent
  input, `value_balance = +value`, transparent change is the RPC's job) but
  emits the **addressed** recipient output via the shared helper instead of a
  zero-diversifier self output. No shielded spends, no shielded change. Returns
  the recipient commitment; no self spend-key (the note is the recipient's).
- **Wallet wrapper** `AttachAddressedShieldOutputBundle(tx, recipient_address,
  value_una, wallet, memo?, persist)` in `shielded_wallet_runtime.cpp`. Decodes
  the address and rejects a bad/`non-dins`/wrong-network HRP **before any tx
  work** (`ExpectedShieldedHrp()` compares `decoded.hrp` to the active chain's
  HRP — `DecodeShieldedAddress` only parses the HRP, it does not enforce
  network). Does NOT persist a note for ourselves; `persist` is accepted only
  for signature symmetry (dry-run fee measurement).

## RPC (`wallet.shield` overload)

`src/rpc/shielded_rpc_json.cpp` — `rpc_wallet_shield` now parses optional
`address` (+ optional `memo`), object form `{amount,fee_una,address?,memo?}`
and array form `[amount,fee_una,address?,memo?]`:

- **No `address`** → byte-unchanged self-shield (existing path, untouched).
- **With `address`** → validate `dins1` + active-network HRP up front
  (`invalid_shielded_address` on failure), then the existing two-pass
  coin-selection / fee-sizing / sign / submit flow calls
  `AttachAddressedShieldOutputBundle` instead of `AttachShieldOutputBundle`.
  Transparent change is attached exactly as self-shield. Result `status` =
  `shielded_to_recipient` and echoes `recipient_address`.

## Tests (the gate) — `src/test/shielded_validation_tests.cpp`

Actual PASS output (`./build/test_shielded_validation`):

```

[ OK ] ShieldedValidationFixture.ShieldToRecipientWrongIvkCannotDecrypt (40 ms)
[ OK ] ShieldedValidationFixture.AddressedRecipientOutputMatchesConventionBytes (78 ms)
...
[==========] 35 tests from 1 test suite ran.
[  PASSED  ] 35 tests.
```

1. **Roundtrip** (`ShieldToRecipientRoundtripValidatesAndDecrypts`): recipient
   keys from a fixed seed → `dins`/regtest address; build a shield-to-recipient
   bundle for 2.5 DIN; `ValidateShieldedBundle` returns **Ok** (commitment,
   output proof, `value_balance = +value`, `transparent_value_delta`); the
   recipient's `ivk` trial-decrypts `encrypted_note` recovering `value_una`,
   `d`, and `rcm`; the recovered `rcm` re-derives `pk_note` and **reproduces
   the on-chain commitment** (proving the note is spendable by the recipient).
2. **cv-binding** (`ShieldToRecipientCvBoundValidatesAndDecrypts`): with
   `cv_bound=true` the addressed output carries a 0x04 proof whose cv matches
   the bundle cv, validates at a post-activation height, and still decrypts —
   exercises the shared helper's `cv_bound=true` branch (audit Critical #1), the
   path every shield-to-recipient tx takes once cv-binding activates.
3. **Negative** (`ShieldToRecipientWrongIvkCannotDecrypt`): a different
   account's `ivk` cannot decrypt — privacy holds.
3. **Parity / KEEP-IN-SYNC** (`AddressedRecipientOutputMatchesConventionBytes`):
   with fixed `rcm`+`esk`, the shared helper's `commitment` equals the
   independently-recomputed on-chain formula and its `encrypted_note` bytes
   equal `EncryptNoteForRecipient` with the same `esk`; a second call with the
   same overrides is byte-identical. Because BOTH the transfer builder and the
   shield builder route their recipient output through this one helper, pinning
   the helper pins both paths.
4. **Backward compat**: the existing `ShieldHelper*` self-shield tests
   (`ShieldHelperProducesValidatorAcceptedTx`, cv-bound, legacy-rejected,
   binds-to-envelope) still pass unchanged — `BuildShieldBundleForTx` and the
   no-address RPC path were not touched.

**Gate proven non-vacuous:** temporarily corrupting the recipient commitment
by one bit made `BuildAddressedRecipientOutput` fail at proof generation and
the roundtrip fail; reverted after confirming.

## Concerns / notes

- The addressed output carries a 611-byte `encrypted_note`; this is the first
  time such an output goes through `ValidateShieldedBundle` in this test suite
  and it is accepted (no length constraint issue).
- `BuildAddressedTransferBundleForTx` had zero prior test coverage in
  `src/test/`; the new parity + roundtrip tests are its first coverage of the
  addressed-output convention.
- End-to-end regtest (tx into a block, recipient wallet sees balance) is marked
  optional in the spec and was not run here; the consensus-level gate (validator
  accept + recipient decrypt) is covered.
- The `invalid_shielded_address` / wrong-network reject paths (in the wrapper and
  the RPC) are **compile-verified only** — they require a WalletManager/daemon
  that the pure-builder test harness deliberately avoids, so they are not
  exercised by an automated test. The decode + HRP-compare logic is a
  straight-line check with a clear error string.
