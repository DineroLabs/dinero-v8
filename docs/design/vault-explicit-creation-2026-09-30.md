# Explicit wallet vault creation and present inventory

Locally qualified with fresh ON/OFF and three full linked-project sanitizer graphs. It is not release readiness.

`vault.create` explicitly inserts one NEW empty authenticated vault in the selected unlocked wallet. It requires the operator address/account, shadow policy, four positive confirmation thresholds, five positive amount caps and queue capacity. It rejects unordered thresholds/caps and validates the exact operator signing scalar/script under the same pinned wallet seed and FULL SQLite transaction before insertion. It does not attach the runtime, issue an address, choose coins, sign, submit, credit an account or infer recovery from absence. Existing vault identities and rows remain unchanged. Each successful explicit create is a separate operation; after a lost response, inspect `vault.list` before deciding to create another vault.

Creation parameters are an array containing one object with exactly these thirteen fields: `operator_address`, `account_id`, `shadow_mode`, `k_observe`, `k_credit`, `k_settle`, `withdrawal_k_settle`, `per_deposit_cap_una`, `per_account_cap_una`, `global_cap_una`, `per_withdrawal_cap_una`, `per_account_outstanding_cap_una`, and `max_queue_depth`. Limits are explicitly chosen by the operator; available backing liquidity is not certified by accepting a limit. The actual HTTP server classifies creation as admin-only. Existing `vault.open` explicitly attaches a selected identity afterward. Legacy automatic runtime must be disabled (`-vault=0`) for that existing-only attachment.

`vault.list` accepts an empty parameter array. One wallet lease/seed and checked FULL transaction capture all present row identities, then authenticate each complete present state and retained wallet-payment binding. SQL types, strict identity order, terminal reads, individual and aggregate byte limits and the final commit are checked. A malformed later row yields an error, never a prefix. Missing storage is an error; no database/schema/identity is created by reads. A present empty table can yield an empty list but certifies no historical absence. Summary fields include identity, revision and optional authenticated operator metadata; historical completeness is explicitly false. The current operational bounds are4096rows and64MiB cumulative encrypted state, refusal rather than truncation; this is not a resident-memory/load qualification.

Vault state owners now read the existing wallet delivery identity inside their own transaction. NULL/malformed/missing identity refuses without generating one. Constructor read failures roll back the transaction it began. A dedicated lease method permits exact signing-key lookup in that lease's existing transaction/seed; ordinary lookup still refuses borrowing a transaction. The dedicated path never begins/commits/rolls back its caller transaction or populates a plaintext cache. Existing HD, canonical imported and historical imported scalar/script authentication is retained.

Patched-path cases cover owned creation/list/reopen and unchanged live routing; HD/import reads under a caller owner; unknown key and commit refusal; late bad rows and interrupted enumeration; absent identity/denied reads/borrowed transactions; actual create/list/open component handlers; benign HTTP admin policy. No original/race/deadlock/barrier/churn reproduction or assertion/deadline weakening. Source inspection caught the ordinary key lookup's intentional transaction refusal before qualification; the new explicit participating API preserves that original contract.

This is present inventory, NOT an authenticated membership/deletion catalog, backup rollback prevention, high-water certificate, cross-store completeness or independent liquidity. It does not migrate historical unbound vaults, add startup discovery, repair legacy economic allocation, settle withdrawals, provide all-consumer acknowledgment or establish whole-node/platform/release readiness. Fresh full ON/OFF and three full linked-project sanitizer graphs are still required. Mainnet unset; no deployment/activation.
