# Selected-chain Orchard admission

The actual MempoolService SubmitBody entry point now routes Orchard bodies through a service-owned selected-chain guard before pool publication. Historical submissions retain their existing path. The guard retains ChainstateService and its activation lock, acquired before the pool lock. Backend-disabled and unimplemented guards refuse admission.

The service checks the active, durable, validated and live-coin parent identities, indexed header/work, configured network/genesis/branch, stateful mode, safe mode and notification-provider presence. It retains the existing consensus-journal audit and, at activation, independently replays the actual selected historical parent. No candidate block identity is fabricated for transaction validation. Postactivation state and anchor ownership must agree with that parent.

Each exact immutable Orchard body is charged against per-transaction block-fit resource limits before proof verification. Confirmed input reads compare durable and live coins, including exact script, value, height and coinbase metadata. Actual transparent signatures, maturity and locks, Orchard proof authorization, active anchors, all action nullifiers and pool value flows are checked against the held parent. Every present pending Orchard body is revalidated against the same parent before adding a new one; a body needing readmission causes refusal without discarding it. Independent deposit and withdrawal reservations must fit the parent balance in any selection order. Pending deposits never fund pending withdrawals. Block bundle/action limits are not applied as a whole-pool capacity limit.

The pool owns input and nullifier conflicts, configured observer capability, checked fees and existing package policy. This initial admission policy requires confirmed transparent inputs and refuses replacements and pending parents. A held empty-scanner registry owner proves no configured Historical-only scanner is skipped. Supported callback captures are prepared before effects. The existing rollback owner and private typed insertion publish exact bodies, input owners, outputs and fee/time indexes. Test-only validation performs no pool effects. Callbacks run after selected-chain and pool lock release; a callback error after publication preserves the admitted outcome.

They cover no-effect preflight, publication/duplicate handling, missing provider, unsupported observer, selected-identity mismatch, invalid signature/domain, immature inputs, pending conflicts, before-commit rollback and after-commit observer failure. Refused structural conflict bodies make no proof-validity claim. A fixture notification provider is not a production implementation or all-consumer acknowledgment.
