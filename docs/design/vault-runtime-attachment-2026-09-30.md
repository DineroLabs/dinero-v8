# Existing authenticated vault runtime attachment

An explicitly created durable vault can now retain its exact operator output script and default credit account in an authenticated DNVS03 snapshot. The script is structurally P2TR and the account is nonempty, has no embedded NUL, and is at most1024 bytes. This routing binding is immutable through ordinary successors. Existing DNVS01/02 states remain explicitly unbound, retain their legacy decoding and are never enrolled from startup defaults. Unbound encoding remains DNVS02. Service capture and every durable mutation preserve the saved binding.

`vault.open [{"vault_id":"<existing 32-byte identity in hex>"}]` attaches an existing authenticated vault from the selected unlocked wallet. It refuses missing/corrupt/foreign/stale owners, historical unbound states and an already initialized runtime. It creates no owner, replaces no singleton, infers no policy and performs no catalog backfill. Use a daemon with the legacy automatic runtime disabled (`-vault=0`) for this explicit attachment path. There is no automatic unlock or create operation. The attached state/policies and operator binding come from the authenticated wallet snapshot. Canonical source callbacks remain mandatory and independently refuse unavailable views; attachment is not chain readiness.

Preparation acquires real WalletService/session/seed/SQLite ownership outside the runtime mutex. It constructs the actual retained-payment dispatcher with a fixed selected wallet and daemon context. Publication checks that runtime lifetime has not changed, then swaps prepared state and publishes the initialized flag last. Runtime configuration cannot change the saved operator script/account; `vault.setoperator` refuses on this durable attachment. No signing-key ownership, complete catalog, historical deletion or backup-rollback certificate follows from a structurally valid operator script.

Before daemon services stop, `CloseVaultRuntimeDispatch` prevents new runtime acquisitions and closes/drains actual wallet dispatch outside the runtime mutex. Closing on an active callback's own thread refuses before teardown; the daemon treats an impossible reentrant teardown contract violation as fail-stop. Final runtime shutdown detaches callbacks. Retained factories cannot reopen closed dispatch. A request already moved to Signing may remain reserved after a closed-dispatch refusal, without creating a payment body. These deterministic component checks are not concurrency, deadlock, crash or power-loss qualification.

The legacy SigningBackend entry point is unavailable on this durable attachment; actual payment preparation, signing, admission and retained-body checks use the existing bound dispatcher. Liquidity health remains explicitly degraded because an independently qualified available-float owner is still missing. No fabricated balance or success is reported for it.

Nine new patched-path cases cover exact encoding and actual encrypted SQLite binding retention/reopen, refusal of add/remove/relabel successors before SQL writes, malformed and truncated frames, checked read/commit failures, existing runtime publication, missing/historical/config/session refusal, dispatch closure, and the actual RPC component. The RPC fixture has no canonical source and verifies that subsequent source use refuses without changing state. A ninth benign HTTP policy case uses an inert callback to require admin access for vault.open; it does not invoke vault attachment or signing. Actual funded production-wallet flow and dispatch concurrency are outside these fixtures. Existing tests/assertions/deadlines remain unchanged.
