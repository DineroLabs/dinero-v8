# Recorded balances and authenticated reservations

The loaded-wallet balance, wallet-info and snapshot handlers use one checked wallet balance summary. The lifecycle lease pins the selected wallet name. A checked FULL SQLite transaction captures the installed payment owner, immutable payment history and recorded coin rows. Required types, ranges, canonical lowercase transaction identifiers, script encodings and terminal SQLite DONE are checked; no summary escapes before COMMIT. The wallet's observed height is captured under its height mutex. No selected-chain callback runs under the wallet lease.

Amounts accumulate in supply-bounded integer units. Confirmed mature coins, unconfirmed coins (including height zero/-1), immature coinbases and spent rows are distinct. Manual locks and authenticated retained payment inputs form a union. Available confirmed amount subtracts only locked confirmed mature coins; locked total also reports reserved immature/unconfirmed coins. The breakdown counts immature coins once. PQ confirmed amounts and per-script available confirmed amounts come from the same captured rows. This is recorded-coin availability, not key-discovery completeness or proof of spendability/chain readiness.

An installed encrypted payment owner needs the unlocked seed. While locked, known coin balances remain visible, `reservation_status` is `unlock_required`, and reservation-dependent locked/spendable/breakdown values are JSON null. A wallet without the payment-owner column reports `untracked`; its manual locks can be counted, but this does not certify historical pending completeness. An available authenticated owner reports `authenticated`. Malformed, failed or incomplete reads raise an error; they are never converted into healthy zero amounts. The aggregate summary has no nonoptional spendable field. Snapshot address availability uses captured exact scripts; absent/unknown script availability is null.

The summary is read-only apart from existing unlock-timeout cleanup in memory and the established FULL transaction durability setting. It does not create an owner, change coin/history rows, release reservations or recreate keys. Supplemental RPC address/history/sync/confidential statistics are still separate reads; the whole RPC is not a cross-store snapshot. Address-index/CSN snapshots and other balance APIs are outside this loaded-wallet change. No deletion/whole-backup completeness, selection authorization, pending lifecycle, admission/readmission or release-readiness claim follows.

Qualification uses actual WalletManager, payment staging and the three loaded-wallet RPC component handlers. Fresh declared ON/OFF builds and project-only sanitizer coverage are required; network JSON transport and production chain/mempool callbacks are outside these fixtures.
