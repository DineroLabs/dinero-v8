# Retained mempool file recovery

Actual mempool load now distinguishes a missing file from an incomplete, unavailable or malformed file. It checks the entire existing version-1 file and exact EOF before returning rows, then decodes every actual-family body before the first canonical admission. Disk fee, height and legacy clock metadata remain non-authoritative. Save serializes actual immutable bodies, with the same 100000-entry bound and a symmetric 512MiB operational file budget; this is not a resident-memory or load qualification.

A dedicated load/save operation owner uses a recursive mutex and an explicit active-operation guard. Concurrent and same-thread reentrant operations refuse. Recovery blocks overwrite before reads or admission; unresolved reads, missing inputs or unavailable family validation retain the original file. The operation retains every decoded body before admission. A successfully resolved retry of that exact path and the same ordered bodies clears the block; a different path, missing file, valid empty replacement or changed body cannot discharge that known pending recovery. Initial absence remains a successful empty start. Partial admitted historical entries can remain in memory during an incomplete load. Their already-present bodies must match exact captured wire bytes before a later retry resolves them. Existing known policy rejection remains rejection, and the established covenant preactivation fixture stays unchanged.

Canonical Orchard bodies can be written and decoded with the enabled backend, but actual Orchard validation remains unavailable and those files retain overwrite protection. The disabled backend refuses such decoding. There is no unchecked admission, historical conversion, new journal or fabricated pending acknowledgment. The actual daemon diagnostic reports incomplete retained recovery rather than claiming an empty pool.
