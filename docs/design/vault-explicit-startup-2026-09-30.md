# Explicit vault startup

The daemon registers vault RPCs while leaving the vault runtime detached. It no longer initializes an empty legacy ledger owner, opens legacy ledger/idempotency files, selects a vault, derives an operator address, or relabels an operator during wallet startup or selection. Legacy `vault=true`/`vault.address` settings produce a migration notice; they do not attach a vault. Existing records remain untouched.

After startup, select and unlock the intended wallet. Use `vault.list` to inspect its present authenticated owners, then `vault.open` with the chosen identity. Use `vault.create` only for an explicitly new empty vault with its full operator and policy configuration. Creation does not attach. Every restart requires explicit attachment; a lost create response should be resolved by listing the wallet before creating another identity. A missing table or an empty present inventory does not establish historical completeness. Legacy ledger files do not contain a complete authenticated owner and are not migrated automatically.

Wallet creation also requires a new name. Legacy positional or named `replace_existing` inputs cannot replace a registered wallet, even when it is inactive or unlocked. The existing creation owner continues to refuse unregistered existing files. The daemon fixture compares every existing wallet row and selected-wallet state before and after rejected calls for encrypted locked/unlocked, inactive, and unencrypted owners. Fresh creation still uses the same initial seed, PQ owner, authoritative recovery binding and checked encryption transition. Whole-create atomicity and complete backup coverage remain separate obligations.

Locally qualified with fresh ON/OFF and three full linked-project sanitizer graphs. The new isolated daemon test covers default detached startup, refusal of financial RPCs before attachment, actual encrypted-wallet create/list/open HTTP calls, two distinct durable owners, restart with authenticated enumeration and explicit reopen, unchanged selected owner rows/address inventory, and preservation of existing legacy files even with the old enable flag. No mining or transaction submission occurs. Fresh full ON/OFF builds, the actual daemon HTTP lifecycle in each configuration, and linked-project sanitizer regressions passed. This is not canonical withdrawal settlement, independently certified liquidity, complete inventory/deletion/backup detection, automatic recovery of old ledger files, all-consumer readiness, or release qualification. Mainnet activation remains unset.

The vendored OpenSSL download keeps its exact version/URL/SHA256 pin and temporary-file cleanup. It now includes receive errors in the existing three retries, with a 1,800-second retry window and unchanged 600-second per-attempt bound. This follows an observed CI curl exit 56 before configuration; it does not retry an unchanged workflow or waive a dependency/test failure. Local loopback transport checks qualify retry/exhaustion behavior only, not a new OpenSSL build.
