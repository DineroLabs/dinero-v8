# PBKDF2 context reuse

Wallet initialization and encryption repeatedly derive keys at their established PBKDF2 work factors. The former implementation invoked the OpenSSL one-shot HMAC API for each round. The new implementation owns one HMAC-SHA512 context per derivation, reinitializes it for each round, and retains the complete PBKDF2 iteration and XOR loops. No process-wide key/context cache is used. Password bytes, salts, KDF versions, work factors, derived valid-input bytes, and wallet envelope formats are unchanged.

Nonempty output requires valid pointers for nonempty input lengths, at least one round, a password representable by the OpenSSL HMAC key-length contract, a representable salt plus counter, and an RFC-valid output block count. Invalid arguments throw before output changes. A zero-output request is inert. Derived output is staged in cleansed storage and copied only after successful completion; intermediate round buffers are also cleansed. Input/output aliasing does not modify the password or salt during derivation. Provider failures throw with caller output untouched. The old accidental zero-round behavior is refused, not treated as a valid KDF version.

A required PBKDF2Compatibility target checks fixed vectors at BIP39 and current/historical wallet work factors, binary/empty/HMAC-block boundaries, multiple output blocks, invalid inputs, aliasing and unavailable-provider refusal. The existing BIP39 target explicitly enables its assert-based fixture in Release builds. Existing wallet suite assertions and deadlines are unchanged.

Private diagnostic evidence establishes exact prototype compatibility and reduced runtime for the unchanged reservation suite. Production qualification must use this final implementation and fresh declared targets; the prototype is not its qualification. Broader release/platform/workload gates remain open. OpenSSL remains an external dependency; project-only sanitizer results do not instrument OpenSSL internals.
