# PQ JSON calls retain the selected wallet session

The five PQ wallet JSON adapters now acquire the real WalletManager database lease before inspecting selection or lock state. They check a requested wallet name against the leased selection, validate the unlock timeout, and retain a cleansed recovery-seed pin until the call finishes. Key copies, derivation, the separate PQ store operation, script registration and result construction occur under that owner. Same-thread reload/lock attempts refuse; the existing lifecycle mutex serializes other-thread wallet changes. An already active caller transaction refuses without being committed or rolled back.

Sign, export and list open only existing read-only storage. Missing storage returns an error and creates no replacement database. Creation and import retain their existing write paths.

The handler parameter structs are passed by value. Their cleanup cannot cleanse the JSON adapter's independent copies. Scoped guards now cover those caller master, BIP32 and imported-seed buffers, the optional derived material, parse buffers and exported raw seed on both ordinary and exception exits. BIP32 derivation also cleanses its own intermediate private key and chain-code arrays. Input JSON and the intentionally returned export JSON remain owned by the RPC transport/caller; this does not claim that all copies of a serialized secret can be erased.

Tests call the actual registered JSON adapters with a real initialized WalletService, WalletManager, UTXOIndex and isolated databases. They cover create/import/list/sign/export with actual signature verification, requested-selection refusal, lock refusal, attempts to lock or reload the same wallet during each separate-store open, caller-transaction refusal and missing-store preservation. The service is kept alive for each test; these are component executions, not HTTP transport, process shutdown, mempool admission or broadcast qualification. Existing mempool stubs isolate the unused chain services; the actual vault runtime links, so the existing daemon-stub file omits only its two conflicting vault definitions for this target. Other targets retain those definitions unchanged.

The lease does not combine the PQ database and main wallet into a single atomic issuance transaction. Existing post-insert script registration, issuance high-water ownership and old store identity/completeness remain separate work. A shared WalletService reference does not make its manager survive an explicit concurrent Stop. The existing HTTP server has a bounded connection-drain timeout; complete shutdown ownership remains an open gate. No account recreation, key regeneration, address relabel, cursor reset, activation or readiness assertion is introduced.
