# Public Orchard release configuration and peer capability

Public network configuration must include an explicit Orchard height and nonzero branch when scheduling the joint compact-proof and 60-second release. Orchard, compact proofs, timing and the joint release must share the same height. All shipped heights remain unset and the branch remains zero. Independent isolated regtest schedules remain supported.

`NODE_ORCHARD_V1` is a separate version-message service bit at bit 30. The production P2P service advertises it only when built with the actual typed Orchard relay, download and runtime graph. Backend-OFF builds and the default standalone version factory do not advertise it. A capability claim is neither binary attestation nor wallet or release readiness.

The P2P service derives the Orchard requirement from the locally validated next-block height, independently of remote height, protocol version and user agent. Inbound/outbound handshakes, established receive/send paths, low-level control sends and idle sweeps require every locally scheduled capability. Rewinding below the boundary removes the requirement. Unset activation never enables it. One captured published-tip height determines both capability requirements outside the peer-map lock; sweep disconnects recheck policy after releasing that lock.

Existing compact/timing helper tests and isolated regtest behavior remain intact. The actual public network-selection fixtures supply an explicit matching Orchard height and synthetic branch, restore both fields on exit, and exercise all fourteen partial combinations of the four coupled schedule fields. Every original selection assertion is retained; mismatched Orchard heights are also rejected. New tests exercise explicit public schedule validation, boundary/rewind/sentinel behavior, invalid-update preservation, actual socketpair handshakes and established peer policy. They are patched-path positive/refusal tests. A mandatory 300-second actual-daemon fixture also performs benign inbound and outbound localhost version/verack exchanges in ON and OFF builds, verifies the exact advertised Orchard bit, retains the existing compact/timing bit, checks the dormant chain stays at genesis and requires clean shutdown. Connect-only mode and disabled discovery keep the fixture local; it does not send transactions or blocks. No production activation or branch ID is assigned.

Locally qualified with fresh full ON/OFF daemon and declared targets, eight ON and seven OFF actual CTests including real inbound/outbound daemon capability advertisement, and twenty sanitizer cases across both complete linked project C++ graphs. External dependencies and the daemon wire process are outside those sanitizer graphs; Linux, public activation and release-wide qualification remain separate gates. This does not install the missing production notification provider, establish all-consumer completion, qualify platform/load behavior, or authorize rollout.
