# Durable batch payment intent before submission

`wallet.sendmany` performs fee-policy preflight through the optional `ITxIngress::Test` capability. Production MempoolService delegates to its existing test-only validation path; an unavailable capability refuses. Preflight may rebuild and sign a candidate without admission or relay. It is not acceptance or continuing chain authorization.

Once preflight succeeds, the actual wallet signing owner retains the final signed body, every explicit recipient and amount, actual fee, selected input metadata, derived reservations and originating send history before the one actual `Submit` call. Actual submission revalidates. Rejection or an exception after submission cannot cause another body to be built or release retained inputs. The response keeps the retained transaction identifier even when the admission result is unavailable. No chain or mempool callback runs inside the wallet lease.

DNPP02 extends the existing complete retained payment envelope with additional explicit recipients. DNPP01 single-recipient records remain readable and retain their original body, intent, fee and timestamp when a batch is added. Recipient matching uses output multiplicity. Staging requires exactly the requested outputs plus at most one authenticated change output. History records the first actual recipient, aggregate recipient amount plus actual fee, existing send category and the actual caller label; the retained record and listing preserve every recipient. There is no invented recipient or label. Explicit replacements cannot reuse another operation's reservations; automatic fee retries occur only before any candidate is submitted.

Amounts use the shared exact DIN-to-una parser and supply-bounded sums. Fee rates are finite, positive and bounded before conversion. Recipient capacity is operational, not a load qualification. Existing installed-owner authentication, history binding, required SQL checks and COMMIT-before-exposure remain in force.

The new component fixtures exercise real signing, wallet database staging, TransactionBuilder and the actual sendmany handler with a controlled ingress adapter and an isolated real UTXOIndex. A narrow fixture friend installs that index without starting chain or P2P services. These cases do not qualify production admission, relay, selected-chain consistency, restart of the whole node or network JSON transport. Separate explicit replacement lineage, consolidation/self-transfer semantics, pending confirmation/conflict/undo/readmission, all-consumer delivery, complete catalogs, rollback completeness and release readiness remain open. Mainnet activation remains unset.

Local qualification used fresh backend ON/OFF full daemon and three declared wallet targets: 56 selected CTests passed in each configuration. All 266 linked project C++ files were freshly instrumented with ASan/UBSan; 18 cases passed with 1,487 stable source inputs. Three scoped omission controls failed their intended assertions and the restored five new cases passed. External libraries were uninstrumented and macOS leak detection was off; this does not extend to daemon or separate wallet binaries. Initial new-fixture pointer compilation errors were corrected before the final builds; no original-source regression claim is made. Existing fixture bodies and 108 prior workflow CTest commands remain unchanged.
