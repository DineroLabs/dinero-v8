`ReserveCatalogSpendForReplay` is a wallet host boundary for pure Orchard-input transfers and withdrawals. It uses the existing lifecycle/SQLite lease and a checked FULL transaction, requires the expected account revision and a generated authenticated catalog, restores every declared current/reached/retained owner and predecessor, requires every account at the captured source head, and reconciles existing operation archives before note selection. Unknown inventory and lagging or missing accounts refuse. No account, seed or key owner is created.

It selects existing unspent notes from the requested restored account, excludes nullifiers reserved across every account, respects the eight-action protocol bound, and checks explicit recipient/output/fee arithmetic. Larger notes are selected first with a stable nullifier tie break. Change receives a real internal receiver. The randomized plan's exact nullifiers, signing message and change counter are retained in the existing encrypted account snapshot in the same transaction. The plan and committed queue return only after checked COMMIT. Proving runs outside wallet/SQLite ownership.

`ReadyCatalogSpendForReplay` authenticates the catalog again and checks the exact existing reservation and expected revision against a consensus-verified authorization with no transparent inputs. The existing queue binds its message, nullifiers and canonical signed body. The full signed bytes commit before returning; an identical Ready retry preserves bytes and revision. A mismatch or failed read, write or COMMIT leaves the prior durable state intact. Neither method submits, relays, clears reservations or reports lasting spend readiness.

Four written ON cases use real wallet creation, catalog accounts 3/17, actual shield funding and proof construction. They cover committed reservations and change with actual transfer admission/mining and encrypted reopen; Ready write/COMMIT rollback followed by actual unshield and canonical undo; reservation SQL/read/COMMIT and amount refusals; and missing/lagging other accounts, session mismatch and borrowed transactions. Tests and production were introduced together; no original-source RED claim.

This is not the complete wallet send RPC or proof executor integration.
