## Actual production path

DaemonApp installs an exclusive wallet payment backend into the existing drained PoolManager/PayoutProcessor lifetime. It replaces the old daemon bool callback that used the selected HD wallet and a fixed fee. New dispatch requires the complete explicitly configured funding policy. The configured wallet name must match the actual selected, unlocked wallet; there is no switch or fallback. Its current session, existing nonzero persistent wallet ID, network and genesis are captured and rechecked. Reading identity does not create one. Wallet and recovery-seed owners are released before pool writes or external dispatch.

A new address group contains at most256 creation-owned allocation origins. The checked FULL pool transaction rechecks the funding policy, every selected payout's current status/origin/address/amount, pool-recorded block eligibility and required worker credit. It writes an immutable attempt with exact member records, wallet identity, network, fees and fresh request ID in the same transaction. Required reads/types/EOF/writes/affected rows/COMMIT are checked. Unique payout and origin membership prevents another concurrent transaction from acquiring the same allocations. Missing historical origins refuse and are never fabricated. Complete present attempt reads reject missing/conflicting member ownership before any wallet operation.

Only the processor call that receives this successful commit invokes DispatchNew. A thrown callback, unavailable preflight, process restart or unknown outcome leaves the existing attempt resolve-only. The actual adapter uses the strict bound wallet request with the exact sorted allocation references; it consults authenticated pending wallet bodies before dispatch and after all handler outcomes. Existing attempts bind their original wallet and fee policy even after configuration changes. They do not select new coins or resubmit when no retained body exists. An absent retained body can therefore require operator investigation; there is no automatic regeneration or retry certificate.

Retained transaction bodies must have exact request/recipient binding, canonical serialization, txid, output script/value and fee limit. The pool records the retained summary in a separate checked FULL transaction. A failed second commit is recoverable from the authenticated wallet body on the next resolve-only pass. Worker pending/paid totals and payout status are unchanged by retention. The returned count means newly retained allocation members, not paid or canonically settled payments. Existing orphan reversal refuses blocks with payment-attempt members, preserving in-flight obligations for explicit canonical reconciliation.

## Limits and open work

Pool attempt/member rows are checked durable metadata, not a cryptographically authenticated pool catalog. Direct SQL mutation, deletion, full backup rollback and cross-wallet completeness are not certified. Wallet retained envelopes authenticate their own request/body bindings. Pool-recorded block confirmations are not independent canonical-chain eligibility. Canonical settlement, orphan/reorg resolution, payment admission/readmission and uncertain-attempt operator workflows remain required before release. The compatibility bool component API remains narrower; production uses the owned backend. No retained transaction is labelled paid. No notification provider is installed and mainnet activation remains unset.
