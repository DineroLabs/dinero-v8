## Settings and RPC

PoolConfig carries an optional named funding wallet, fee-rate hint and maximum transaction fee in una. There is no implicit wallet or fee ceiling. All three fields are supplied together, or the policy is unset. Explicit zero values remain operator intent; they do not promise a zero-fee transaction. Wallet names are nonempty, at most256 bytes and contain no NUL. Fee values are exact nonnegative integers bounded by the money supply constant.

Four typed configuration rows record a state plus the three fields. All four absent is the predecessor unset state. Partial, malformed or conflicting sets refuse; an explicit unset state requires the other three values to be empty. No missing values are reconstructed. Complete checked reads require terminal SQLITE_DONE. The existing checked FULL settings transaction writes all fourteen settings together and preserves the prior live policy on required-write or COMMIT refusal. Unknown unrelated typed settings retain the prior preservation behavior. Whole-database rollback and deletion are not authenticated by these settings.

Actual pool.setconfig captures one strong runtime manager, parses the requested changes, then compares the complete expected live configuration under the manager lock. A stale request refuses instead of overwriting a newer update. The manager preallocates its replacement configuration and calculator before the database commit and publishes with nonthrowing swaps afterward. This compare-and-set covers manager-owned updates; direct independent database writers and multiprocess ownership remain outside its scope. Actual pool.getconfig reports the optional policy as null or an exact three-field object. Both existing RPC integer and DIN conversion inputs now refuse negative, nonfinite, overflowing or incorrectly typed values before conversion. Existing fractional DIN truncation remains unchanged; no new decimal rounding claim is made.

## Scope

This is explicit configuration and its actual RPC/configuration owner, not funding-wallet authentication, an allocation catalog, durable payment authorization or canonical settlement. No wallet is opened and no payment is signed or sent by this transition. The existing production bool payout callback does not yet consume this policy; unset or cleared policy therefore does not by itself stop that legacy path. The subsequent durable payment owner must bind the configured wallet's persistent identity and network, commit immutable allocation membership and fee policy before calling the wallet, and resolve uncertain attempts from authenticated retained transaction bodies. Retention alone must not mark a payout paid. Production dispatch wiring, in-flight orphan handling and settlement remain open.
