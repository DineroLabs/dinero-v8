# Atomic orphan accounting for pool payouts

Locally qualified with fresh full dinerod, replay and daemon lifecycle targets ON/OFF; twelve actual selected CTests passed in each configuration. Four new actual PoolManager/PoolDB cases passed in each. All 41 selected ON component cases passed with the complete linked project-C++ graph freshly ASan/UBSan instrumented. Actual linked source counts are retained in the private receipt. External/Rust/C/PQClean remain uninstrumented and macOS LSan is off; daemon entry point and OFF are outside this sanitizer graph. Exact Linux and release qualification remain separate. No unsafe originals or synchronization-removal controls.

Every PoolDB member serializes its SQLite connection. The recursive connection owner spans existing DB-only transaction callbacks and prevents direct PoolDB callers from joining another thread's transaction. Callers acquire PoolManager before PoolDB; DB-only callbacks must not acquire manager or selected-chain owners. Object lifetime remains the manager's responsibility.

PoolManager's orphan handler calls one checked FULL transaction. It captures the requested block and every present payout with checked SQL types, ranges, owner text, active-worker balance and terminal completion before writes. It checks each bind, step, affected row and COMMIT. Missing blocks are explicitly distinct from failed reads. Missing workers and malformed or interrupted inventories refuse. Borrowed transactions are untouched. Failure preserves the caller's result and rolls back this transition; the summary is published after COMMIT.

The existing accounting policy is preserved: PAID and FAILED payouts remain untouched; PENDING and CONFIRMED payouts debit the worker's pending balance with the existing saturation at zero, then become FAILED with empty transaction ID, zero paid time and the existing orphan reason. The block becomes orphaned in the same transaction. Payout amount, retry fields and other metadata remain unchanged. Repeating the operation does not debit already-failed payouts. This does not refund previously paid payouts or introduce a reactivation/allocation policy.

The new component cases exercise actual PoolManager/PoolDB, reopen, paid/failed preservation, insufficient pending balance, late write and commit refusal, malformed later rows, missing worker, denied read, interrupted completion, caller transaction ownership and FULL-before-BEGIN ordering. Actual normal ON/OFF and complete project-linked sanitizer results are recorded above and in the private qualification receipt. No unsafe originals, synchronization-removal controls or race reproductions are used.

This is one accounting transition, not coherent canonical-chain discovery, payout broadcast ownership, reorg reactivation, complete pool recovery, production notification-provider installation or all-consumer acknowledgment. Existing general pool getters retain narrower contracts. No deployment, mainnet activation or release-readiness claim.
