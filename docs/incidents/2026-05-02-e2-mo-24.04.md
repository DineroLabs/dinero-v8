## Why this record exists

Phase E.2 of the Core 1.0 plan (per
[`docs/operations/core-discipline-plan.md`](../operations/core-discipline-plan.md)
§3) is the gate that proves a fresh `dpkg -i` of the package
produces a working node. Docker-only validation cannot prove
systemd integration, journald behavior, real-VPS port permissions,
or service-user ownership semantics — so the gate must run on a
real Linux host.

MO (Ubuntu 24.04 LTS) was selected as the controlled-maintenance
staging target. Production fleet (CN/LA/VA) was NOT touched during
the original E.2 run.

## Caveat: `dinero-cli health` returned FAILING

`dinero-cli health` returned `FAILING tip undo data missing` (exit
code 2). This is **NOT a packaging or install failure.** The same
condition reproduces on production CN/LA/VA which are running the
pre-Phase-E binary path:

```
status_flags by sampled height:
  h ≤ 10783: 399/415  (HAVE_UNDO bit SET — May 1 repair)
  h ~ 11000+ (MO):    143  (HAVE_UNDO bit CLEAR)
  h ~ 12000+ (CN):    159  (HAVE_UNDO bit CLEAR)
```

The transition height differs per node, depending on when each
node mined past the May 1 repair. This is a **pre-existing
fleet-wide regression**: the live ConnectTip path stopped writing
the `BLOCK_HAVE_UNDO` status flag at some point after May 1. The
health command from Phase D.4 (`tip_undo_present` check) is doing
exactly what it was designed to do — surface the bug class that
caused the Apr 30 incident.

**This is a release blocker for later phases (E.3 onward)** but
NOT a Phase E.2 install-gate failure. Phase E.2 proved the .deb
installs and runs cleanly; the FAILING health is an external
finding the install gate happens to surface because the operator
can finally invoke `dinero-cli health` on the .deb-installed node.
